# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this app is

Portreaper is a macOS + Windows menubar/tray desktop app that finds processes listening on TCP ports and helps the user kill orphaned dev-server "zombies" (e.g. a `vite`/`node`/`cargo run` process whose launching shell died). It also surfaces **orphaned dev processes that hold no port at all** (e.g. an `electron-vite` Electron main process left behind when its parent `node` is killed — adopted by launchd, listening on nothing) — these are invisible to a port scan but are exactly the kind of dev residue users want reaped. It is **not** a generic port viewer — the core value is the zombie-suspect classification (with confidence tiers) and the launcher-chain UI.

Stack: Tauri 2 + React 19 + TypeScript 7 + the **Vite+ toolchain** (`vp` — wraps Vite 8/Rolldown, Vitest, Oxlint, Oxfmt), package manager is **pnpm 11**. UI is bilingual (zh/en) via `src/i18n.ts`.

Vite+ specifics: `vite` is aliased to `@voidzero-dev/vite-plus-core` via the pnpm catalog in `pnpm-workspace.yaml` (vitest/oxlint/oxfmt come bundled — they are **not** direct devDependencies; test files import from `vite-plus/test`). Git hooks live in `.vite-hooks/` (wired by the `prepare` script), in **two layers**: **pre-commit** → `vp staged` runs only the auto-fixable formatters over staged files (the `staged` glob config sits in `vite.config.ts` and must be maintained by hand — the function-form config defeats `vp migrate`'s auto-merge; the globs cover JS/TS/JSON/YAML/TOML **and `*.rs` via `rustfmt`**, because `vp check` is JS/TS-only and Rust format had no local gate at all until v0.7.2); **pre-push** → `.vite-hooks/pre-push` mirrors the CI gate (vp check, `pnpm run typecheck`, vitest, vp build, cargo fmt/clippy/test, the five guard scripts + their self-tests, version-consistency check, `node --check` over `website/*.js`, plus the Raycast typecheck **only when** `integrations/raycast/node_modules` exists — the one allowed local gap, CI covers it unconditionally) and blocks the push on any failure — ~10s incremental. It deliberately skips the two cross-target `cargo check`s (x86_64-apple-darwin, x86_64-pc-windows-msvc — they need `rustup target add` / `llvm-rc`), which stay CI-only. Escape hatch: `VITE_GIT_HOOKS=0 git push`. Both layers exist because format-only slips turned main red on v0.6.0 / v0.7.0 / v0.7.2 — **keep the glob and the pre-push list in sync whenever a CI step is added**. **Markdown is excluded from oxfmt via `.prettierignore`** — oxfmt 0.2.6 corrupted md content (rewrote a fenced block in a list item into inline code; dropped a blockquote `>` prefix), so never widen fmt scope to `*.md` without re-verifying. `AGENTS.md` is the Vite+ scaffold block — leave it.

## Commands

```bash
pnpm install           # first-time setup (also wires git hooks via `prepare` → vp config)
pnpm tauri dev         # run the desktop app (launches vp dev/vite on :1430, then tauri webview)
pnpm tauri build       # produce a .app/.dmg (macOS) or NSIS .exe (Windows)
pnpm build             # tsc --noEmit + vp build (used by tauri build)
pnpm exec vp check     # oxfmt + oxlint gate (CI-enforced); --fix to apply; md excluded (see below)

# Cargo commands run from the REPO ROOT (workspace root) and must be workspace-wide:
# members are crates/portreaper-core (the engine) + crates/portreaper-cli + src-tauri (the GUI shell).
# A bare `--manifest-path src-tauri/Cargo.toml` silently skips the engine — i.e. skips
# every line of logic these gates exist to protect.
cargo fmt --all --check                    # rustfmt gate — CI-enforced, and NOT covered by `vp check` (which is JS/TS only)
cargo test --workspace                     # 70+ unit tests incl. classify fixtures
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace live_scan -- --ignored --nocapture   # real-machine smoke: scan this Mac

pnpm test                                  # frontend regression tests (vp test run: bundled vitest + happy-dom)
pnpm run typecheck                         # tsc over BOTH projects: tsconfig.json (webview code — deliberately no node types) + tsconfig.test.json (tests + fixtures, with node types); CI/pre-push use this, not bare tsc

# Windows cross-compile check from macOS (needs `brew install llvm` for llvm-rc):
PATH="/opt/homebrew/opt/llvm/bin:$PATH" cargo check --workspace --target x86_64-pc-windows-msvc

node scripts/check-reason-parity.mjs       # Rust ReasonCode <-> i18n/render-path guard
node scripts/check-release-assets.mjs      # stable asset names (release.yml/website/README) + website i18n keys
node scripts/check-paths-parity.mjs        # bundle identifier: core paths.rs <-> tauri.conf.json (a split forks whitelist.json per frontend)
node scripts/check-toolchain-parity.mjs    # Rust toolchain version: rust-toolchain.toml <-> ci.yml <-> release.yml
node scripts/check-model-parity.mjs        # ProcessEntry/ParentRef field sets: Rust model.rs <-> src/model.ts <-> raycast cli.ts
node --test scripts/*.test.mjs             # guard-script self-tests
node scripts/bump-version.mjs --check 0.1.0
```

The Rust toolchain is pinned by `rust-toolchain.toml` (constrains local dev, CI, and release builds alike; the upgrade steps are documented in that file — keep the workflow files in sync). CI (`.github/workflows/ci.yml`) runs the full gate on macOS + Windows; the macOS leg additionally cross-checks `x86_64-apple-darwin`, runs the guard scripts + version-consistency check, and typechecks the Raycast extension (`npm ci --prefix integrations/raycast && npm run typecheck --prefix integrations/raycast` — the extension is otherwise outside every workspace gate). Release is tag-triggered (`v*`, see `docs/RELEASING.md`). PR review is CodeRabbit (`.coderabbit.yaml`): its `path_instructions` mirror the invariants in this file — when an invariant here changes, update the matching block there (it deliberately disables clippy/oxlint to avoid double reports). The GUI crate is `portreaper_lib` (see `src-tauri/Cargo.toml [lib]`); `main.rs` is a thin entry point calling `portreaper_lib::run()`.

**Cargo workspace layout** (roadmap + rationale: `docs/ARCHITECTURE-CORE-SPLIT.md`): members are `crates/portreaper-core` (the engine) + `crates/portreaper-cli` (headless frontend, feeds Raycast) + `src-tauri` (the GUI shell). The Raycast extension itself lives in `integrations/raycast/` — a separate npm project (own `package-lock.json`, **not** part of the pnpm workspace) that installs the released `portreaper-cli` binary and verifies it against `portreaper-cli-SHA256SUMS`. Maintainer notes (Store submission checklist, real-machine QA log, the pitfalls behind each decision) live in `docs/RAYCAST-MAINTAINING.md` — deliberately **outside** the extension directory, because `ray publish` submits that directory verbatim into a public raycast/extensions PR. Keep `integrations/raycast/` limited to what the Store submission needs; the metadata screenshots are regenerated by `scripts/capture-raycast-metadata.sh`. **The extension is English-only by design and has no i18n dictionary** — the Store accepts US English only, and `src/i18n.ts` is unimportable there anyway (it touches `localStorage`/`navigator` at module top level); its user-facing strings are inline English literals, and verdict reasons render as raw engine codes (`ppid1_orphan`). It also gets **no Dependabot npm updates** — Dependabot's pnpm probe rejects any subdirectory under a repo-root pnpm workspace regardless of that subdirectory's own layout, so `npm outdated --prefix integrations/raycast` before a Store submission is the manual substitute (both facts are recorded where they bite: `.coderabbit.yaml`'s raycast rule and `.github/dependabot.yml`'s header). The workspace root is the *repo root*; `target/` and `Cargo.lock` live there, **not** under `src-tauri/`. Three consequences that bite if you forget them: `Swatinem/rust-cache` keys on `". -> target"` in both workflows; `release.yml`'s dmg post-processing globs `target/<triple>/release/bundle/…`; and `scripts/bump-version.mjs` reads `Cargo.lock` from the root while still reading `Cargo.toml` from `src-tauri/` (that asymmetry is deliberate — the lockfile belongs to the whole workspace, the version belongs to the app crate). `src-tauri/.gitignore` **keeps** its `/target/` line on purpose: oxfmt scopes itself by gitignore, and a pre-split checkout with a leftover `src-tauri/target/` would otherwise make `vp check` crawl into cargo's fingerprint JSON.

## Architecture

### Two-process structure

- **Frontend** (`src/App.tsx` + `src/useScan.ts` + `src/components/` + `src/model.ts` + `src/describe.ts` + `src/i18n.ts`): polls `scan_ports` every 2 seconds, renders the table, owns the kill-confirm modals and search/filter, pushes counts into the tray via `update_tray_title`. `App.tsx` is the container (kill/sweep/whitelist flows); the polling loop with its in-flight-reuse and `freshScan` (wait-then-rescan) semantics lives in the `useScan` hook — directly unit-tested in `useScan.test.ts`, don't inline it back. Presentation lives in `src/components/`: `ProcessRow.tsx` (the memoized row — props are `{e, expanded, shared}` where `shared` is a single identity-stable context object so `rowPropsEqual` never needs a hand-maintained field list), `ProcessDetail.tsx` (expanded panel: chain, resources, evidence/exemption lists), `Section.tsx` (the suspect/healthy/starred group wrapper), `ConfirmModal.tsx` (the destructive-confirm skeleton + Tab focus trap) + `KillConfirmModal.tsx`/`BatchConfirmModal.tsx` on top of it. All strings go through the typed i18n dict — a missing English key is a tsc error; dynamic key families go through the narrowing helpers in `i18n.ts` (`reasonKey`/`storyKey`/`verdictKey`…), never `as I18nKey` in components. Test fixtures share one serde-mirror (`src/test-fixtures.ts makeEntry`) — the only hand-written copy on the test side. Pure logic lives outside the component file so it is unit-testable: `model.ts` holds the `ProcessEntry` serde mirror, `legacyWhitelistKey`, `REASON_PRIORITY`/`EXEMPT_REASONS` (read by check-reason-parity) and format/error helpers; `describe.ts` holds the "what is this" knowledge base — its **brand-scoped patterns are skipped for `dev-script` and `automation-instance` rows** (a project dir named `spotify-clone` lands in `app_label`, and a real brand process is never one of those categories — their identity comes from the command line).
- **Engine** (`crates/portreaper-core/`): scanning, classification, process termination, **plus the shared persistence layer** — `whitelist.rs` (the `Whitelist` value type: load/add/remove with atomic write) and `paths.rs` (Tauri-free per-environment directory resolution + `APP_IDENTIFIER`) — with **zero GUI dependency** (its reference count for `tauri` is 0 and must stay 0). This crate is the single source of truth for the zombie/orphan verdict **and** for where the whitelist file lives: the whitelist is shared state across all frontends (a star added in Raycast must be visible to the desktop app's next scan), so the directory algorithm byte-replicates Tauri's (same `dirs` major as tauri — if a tauri upgrade bumps it, sync here). Facade exports: `Scanner` (long-lived, holds the CPU-sampling state for the GUI's 2s poll) / `scan_once` (one-shot, CLI) / `kill` / `Whitelist`. Every invariant below lives here.
- **Desktop shell** (`src-tauri/src/`): the tray and window lifecycle — no verdict logic, no path/whitelist algorithm of its own. `commands.rs` (all `#[tauri::command]` fns — thin wrappers over the engine + the modules below), `whitelist.rs` (GUI-only process-wide singleton over `portreaper_core::Whitelist` — a lifetime policy, not logic: the *instance* lives forever, its *contents* do not. `get_all()` calls `refresh()` every scan because the whitelist is shared across three frontend processes — see the invariant below), `paths.rs` (thin Tauri adapter over `portreaper_core::paths` + the `assert_matches_tauri` runtime drift assertion, see below), `lib.rs` (builder, tray, menus, window events).

All frontend↔backend communication is Tauri `invoke()` calls: implement in `src-tauri/src/commands.rs`, register in `lib.rs` (`invoke_handler![...]`). Permissions (`src-tauri/capabilities/default.json`) are an **exact whitelist guarded by `src/security-config.test.ts`** — that test also pins the strict CSP (no `unsafe-inline` anywhere, `connect-src` must keep both Tauri IPC carriers). Adding any permission or touching the CSP requires updating those assertions deliberately.

### Scanner module layout (`crates/portreaper-core/src/scanner/`)

Platform variance is isolated in two leaf files with **identical cfg-gated function signatures** (compile-time polymorphism, no traits):

```
crates/portreaper-core/src/
  lib.rs             crate facade: pub use Scanner/scan_once, kill, Whitelist, ProcessEntry
                     consumers go through the ROOT re-exports (`portreaper_core::scan_once`),
                     not module paths — paths/whitelist stay `pub mod` because they carry more
  scanner/mod.rs     orchestration: collect → (per-PID) build_entry [snapshot → classify → chain walk] → sort
                     two scan paths share build_entry: (1) listeners from lsof/GetExtendedTcpTable;
                     (2) orphan dev processes — full-process-table rows that hold no port
                     also owns the app-category constants (DEV_SCRIPT_CATEGORY, …) — production
                     code never spells the wire strings; tests keep the literals on purpose
  scanner/model.rs   ProcessEntry (serde contract with src/model.ts), ProcMeta, ProcessSnapshot
                     + the shared `#[cfg(test)] ProcMeta::fixture` (was hand-copied 5×)
  scanner/classify.rs  PURE classifier + ReasonCode/Confidence enums + fixture tests.
                     Also `is_dev_like` — the ONE definition of "dev-like", shared with mod.rs's
                     orphan gate (they were two convention-synced copies). Fixture reasons are
                     asserted as ORDER-INDEPENDENT SET EQUALITY: an extra reason fails the table,
                     which is exactly the bug class this project has shipped twice.
  scanner/chain.rs   parent-chain walk: ChainFlags, build_parent_chain, pm2 predicates
  scanner/postprocess.rs  cross-entry post-passes: mark_duplicates + fill_subtree_cpu
  scanner/identify.rs  shared, separator-agnostic path/project/script helpers + `AppIdentity`
                     {label, category} + `script_identity_step` (ladder step 0, shared by both
                     platforms, per-platform differences injected as params) + dev-keyword tables
  scanner/macos.rs   lsof + ps + launchctl list; macOS path ladder
  scanner/windows.rs GetExtendedTcpTable + sysinfo; SHGetKnownFolderPath path ladder
  platform.rs        kill with start-time identity check (PID-reuse guard)
  paths.rs           Tauri-free per-env dirs + APP_IDENTIFIER (shared by GUI/CLI/Raycast)
  whitelist.rs       Whitelist value type — one shared whitelist.json for all frontends
                     (`Whitelist::detached()` is the no-disk degraded form — deliberately no path param)
```

**Platform semantics live in the leaf files, never in the orchestrator.** Both `macos.rs` and `windows.rs` expose the same cfg-gated signatures, and that set includes the chain-termination hooks — `chain_hits_init` *and* `dead_root_terminates_chain` (macOS `false`: a dead root is a transient, PID 1 is the real init; Windows `true`: the parent simply vanishes, there is no init to hit). `chain.rs` calls the hook; a runtime `cfg!(windows)` inside the orchestrator is the thing this replaced.

Data sources: macOS = `lsof -iTCP -sTCP:LISTEN -P -n -FpcLn` + `ps -A -o pid=,ppid=,state=,tty=,etime=,pcpu=,rss=,user=,command=` (user fills the otherwise-empty column for port-less orphans; listeners still prefer the lsof `L` field) + a second `ps -A -o pid=,comm=` (comm is the authoritative exe path — it survives spaces in paths, unlike splitting the command line) + `launchctl list` (managed-PID set). Session leaders are identified by the `s` flag in the ps *state* column — **never** use `ps -o sess=`: on macOS it prints 0 for every process (review-caught bug that made every terminal process look session-orphaned). Windows = `GetExtendedTcpTable` with `TCP_TABLE_OWNER_PID_ALL` (IPv4+IPv6, no subprocess), split by `dwState` into LISTEN + ESTABLISHED rows, + a long-lived `sysinfo::System` (the 2s poll provides the CPU sampling interval; first scan shows 0% CPU by design). `LANG=en_US.UTF-8` is forced on all macOS subprocesses.

**ESTABLISHED probing is asymmetric by design** (its only consumer is the automation-instance liveness veto): Windows gets the whole connection table for free from the same call, so it collects it and then narrows to automation PIDs; macOS runs a *second, PID-scoped* `lsof -a -p <automation pids> -iTCP -sTCP:ESTABLISHED -Fpn` **only when that candidate set is non-empty** (zero cost on a normal machine). Never widen the main LISTEN lsof to all states to get this — lsof is the single most expensive call in the project.

### Classification v2 (the product's core logic)

`classify(&ProcessSnapshot) -> Verdict` in `classify.rs` is a **pure function** — every OS probe is precomputed into the snapshot by `mod.rs`/the platform collectors, so the decision tree is table-testable on both platforms. Decision order:

1. `state` contains `Z` (defunct) → always suspect, `Confirmed`.
2. **Hard exemptions** (in order): `launchd_managed` (launchctl claims the PID — covers brew services, LaunchAgents) → `automation_instance && debugger_attached` (a client is driving it right now) → `exe_is_standard_install` → `brew_service_path` (fallback for system-domain brew services launchctl can't see) → `pm2_managed`.
3. Orphan signals: `direct_orphan` (macOS: PPID=1; Windows: parent missing or parent created *after* child = PID slot reused), `chain_orphan` (parent chain ends at init/dead root without passing a live user-visible app, and the leaf is dev-like or an ancestor shell is itself orphaned), `tty_orphaned` (real ttys with no session leader — dead terminal session).
4. No signal → not a suspect.
5. `elapsed_secs < 10` → `Possible` + `just_reparented` (grace period; never swept).
6. Tiers: orphan×dev or orphan×dead-session → `Confirmed`; bare orphan/chain → `Likely` (exception: a Windows bare `ParentExited` with no other corroboration → `Possible` — Squirrel/Electron bootstrappers exit by design, fixture-pinned); session-only → `Possible`. ("dev" here = `dev_keyword || dev_category || automation_instance`.)

**Invariants — do not break:**
- Standard install path / launchd-managed ⇒ never auto-flagged.
- **Exception to the path rule #1:** `dev-script` category is *not* exempted by the interpreter's exe path — a script runtime's identity is its *script*. `/usr/bin/python3 app.py` and `C:\Program Files\nodejs\node.exe vite.js` must remain detectable (`identify_app` classifies by script location first). The same applies to `-m <module>` invocations (`identify.rs extract_module_arg`): an orphaned `python -m http.server` is `dev-script` regardless of where the interpreter lives, and the `brew_service_path` exemption is decided by the *identity path* (`mod.rs brew_service_exemption`) — the script's location when there is a script, never the interpreter's for `-m` calls; the interpreter path is only the conservative fallback for bare/console-script invocations (keeps system-domain brew python services exempt).
- **Exception to the path rule #2 — `automation-instance`** (`identify.rs is_automation_instance`, ladder step 0b on both platforms; fixed in v0.7.2, case archived as Gap 1 in `docs/KNOWN-GAPS.md`): a throwaway automation browser's identity is its *command line*, not where the browser binary is installed. A headless Chrome started by Playwright / Puppeteer / a devtools MCP lives in `/Applications` (or `Program Files`) and would otherwise take the `installed-app` hard exemption and never be flagged, however long it spins. Judgement is deliberately two-sided and **both halves are load-bearing**:
  - **Detection needs `--headless` AND one session marker** (`--remote-debugging-port` / `--remote-debugging-pipe` / `--enable-automation` / marionette, or a `--user-data-dir`/`-profile` pointing into a temp dir). `--headless` is a *necessary* condition — dropping it makes the rule match every **headed** automation instance, i.e. the browser window the user is looking at right now. The temp-dir test reads *argument values* and must never reuse `is_standard_install_path`: `/private/var/folders/` is an *exemption* there (App Translocation) and *evidence* here.
  - **`DebuggerAttached` vetoes everything** (hard-exemption step 2): if any ESTABLISHED connection's **local** port is one of this PID's listening ports, a client is driving it — exempt, no matter how orphaned it looks. Match the *local* side only: a residual browser scraping the web has plenty of outbound ESTABLISHED sockets, and counting those re-hides Gap 1's main case. This signal is **exemption-only, never a confidence upgrade** (connections flap; upgrading on them would make rows flicker).
  Also `brew_service_exemption` returns false outright for this category — a brew-installed `chromium` running headless must not be shielded by its Cellar path.
- **Two path predicates, never interchangeable** (`mod.rs build_entry`): `is_standard_install_path` is the **exemption policy** and deliberately errs toward `true` (macOS counts `/private/var/folders/` to make room for App Translocation; Windows returns `true` for an **empty** exe path when MSIX/elevated processes hide it) — it drives the verdict, where over-trusting is the safe direction. `is_conventional_install_path` is the **factual** one, with those carve-outs stripped, and feeds only the user-facing `NonstandardPath` reason. Reusing the exemption predicate to state a fact means every future widening of it (its whole purpose is to widen) silently makes the UI lie — an orphaned `go run` artifact really does live in `/private/var/folders/`, which is exactly where that reason is most true. Same lesson as `identify.rs is_temp_dir_path` ("两者语义相反，绝不能共用同一个函数"). Homebrew is deliberately *not* in either list (brew services exempt via `brew_service_path`), so brew-installed interpreters do keep the reason.
- **`OrphanedChain` is listed only when the walk actually saw an ancestor** (`ChainFlags::walked_real_ancestor` → `ProcessSnapshot::chain_walked_real_ancestor`). Every platform's direct-orphan condition (macOS `ppid==1`; Windows `ppid==0` / parent absent from the table) makes `build_parent_chain` terminate on its **first iteration**, so "chain ends at init" is then a restatement of the direct-orphan reason and the detail panel showed both as if they were independent corroboration. Key on that structural fact, **never on the `ReasonCode` variant** — the variant form (`!= Some(Ppid1Orphan)`) misses Windows' `ParentExited`, which implies chain termination just as much. Reason-only: confidence tiering reads the `chain_orphan` variable, so it is unaffected either way.
- **`cpu_percent_tree` is display-only** (`mod.rs fill_subtree_cpu`, filled in a post-pass over the already-collected process table — no extra syscall). Headless browsers burn CPU in `--type=gpu-process` children while the listed main process reads ~0%, so the row alone hides a fully pegged process tree. It deliberately **never enters `ProcessSnapshot`**: the verdict means "unclaimed", not "power-hungry" — a healthy `vite build` pegs a core too. The DFS keeps a `visited` set; a ppid cycle in the snapshot would otherwise hang the whole scan.
- The chain walk stops at any live user-visible app: `installed-app` category, any `.app/` bundle on macOS (stock Terminal.app lives in `/System/Applications/`!), and live session roots on Windows (`explorer.exe`, `services.exe`, ... — without this every cmd-launched dev server would be a false positive, since Windows chains all end at the exited `userinit.exe`).
- The flagged process is always the **port-holding leaf**, never an intermediate shell.
- Sweep ("一键清扫") and the tray count cover `Confirmed`+`Likely` only; `Possible` is never swept.
- **Duplicate dev-server detection** (`mod.rs mark_duplicates`, cross-entry post-pass after the pure per-entry classify): two dev-script listeners are duplicates when ports are disjoint, they are not parent/child, and (a) the full command is identical, (b) the path-derived (project, script/module) identity matches, or (c) cwd is identical + script/module identity matches (catches "Warp started :5173, VS Code started :5174 of the same project"). **cwd is the strongest evidence and a known-different cwd vetoes the pair** — hoisted node_modules collapses path-derived project names to the monorepo root and even makes full commands identical across distinct apps, so monorepo sub-packages / git worktrees are only told apart by cwd (collected for listener PIDs only: macOS `lsof -d cwd`, Windows `sysinfo cwd()`). A live common non-shell, **non-user-visible-app** parent or grandparent (concurrently/cluster/turbo) marks intentional multi-instance, never duplicates; a shell ancestor, a user-visible app ancestor (`is_chain_stopper` — two tabs of the same Terminal/iTerm are independent sessions, not an orchestrator), or a dead/synthetic parent does **not** exempt (re-running in one terminal, or a co-reparented orphan pair, is exactly the target). `duplicate_of` always points at the **smallest peer PID** (deterministic across the HashMap iteration order; ≥3 instances used to flicker). Duplicates only ever reach `Possible` (+ `duplicate_of` peer PID) — the machine cannot know which instance the user is using, so they are **never swept**.
- **Orphan dev processes (second scan path in `scan()`):** the full process table (already collected via `ps -A` / `sysinfo` for the chain walk — no extra syscall) is swept for processes holding no port. Inclusion gate is **stricter** than for listeners — a row must be **dev-like** (`dev_keyword || dev_category || automation-instance`) *and* classify as a suspect. Without the dev-like gate the dozens of normal `ppid==1` system daemons would flood in: a port is the listeners' "worth-attention" evidence, dev-likeness is the orphans'. Whitelisted orphans still surface (so the user can un-star); non-suspect dev processes (a healthy `vite` in a live terminal) are not listed. A cheap dev-like pre-gate skips the parent-chain walk for non-dev rows. Orphan entries have empty `ports` (frontend shows a "no port" badge).
- **Dev-tool runtime paths are `dev-script`, not `installed-app`** (`identify.rs is_dev_tool_runtime_path`, used by both platforms' `identify_app`): electron/electron-vite ship `Electron.app` under `node_modules/electron/dist` and Playwright/Puppeteer download `Chromium.app` into `~/Library/Caches/ms-playwright` / `~/.cache/puppeteer` (Windows: `%LOCALAPPDATA%\ms-playwright`), all byte-identical in form to a real installed app. Without this an orphaned dev runtime would be exempted as an installed app and never detected. These path fragments are a zero-false-positive signal — user-installed apps never live there. Keep the list in that one shared function (it used to be a per-platform literal, which drifts).
- **The whitelist is shared mutable state across three frontend processes, and both directions must work.** The *write* direction is `Whitelist::add`/`remove` merging from disk before saving (a resident GUI must not clobber a star the CLI just added). The *read* direction is `Whitelist::refresh()`, called by the GUI's `whitelist::get_all()` on **every** scan — a resident process that caches contents never sees an external star, so the row keeps showing as a suspect, keeps counting in the tray, and **keeps sitting in the sweep target set**: one-click sweep then kills the process the user just starred in Raycast. That regression shipped in v0.8.1 and was caught on real hardware by the cross-frontend ★ check in `docs/RAYCAST-MAINTAINING.md`; it is pinned by `whitelist::tests::resident_instance_sees_external_changes_without_mutating` (engine semantics) **and** `src-tauri` `whitelist::tests::get_all_picks_up_changes_written_by_another_frontend` (that the GUI actually calls it). `refresh()` is **replace**, never union — un-starring has to propagate too. Never reintroduce a contents cache here; the read is a few hundred bytes next to lsof + two `ps` + launchctl in the same scan.
- Whitelist (`is_whitelisted`) still lists the row, forces `is_zombie_suspect=false`, excluded from sweep/tray. Key (`scanner::mod::whitelist_key`): `exe_path` **only when it contains a path separator** — a PATH-resolved bare interpreter name (`ps -o comm=` returns just `node` for `node app.js`/shebang shims) would collapse the key across every same-named listener and whitelist them all, so bare names fall back to the full command line (then lsof `command`). **Every frontend reads the engine-emitted `ProcessEntry.whitelist_key` and never re-derives it** — both the desktop UI and the Raycast extension used to carry their own copy of that rule, which is exactly the "each frontend re-implements the verdict" failure the core split exists to kill. `legacyWhitelistKey` is the one remaining frontend-side derivation, and only because the engine does not emit the v0.4.0 key.

`ReasonCode`/`Confidence` serialize as snake_case/lowercase and are rendered in the frontend through four key families: `reason.*` + `reasonTip.*` (detail panel, every code), `story.*` (inline primary-reason story, positive codes only), `verdict.*` (inline confidence prefix). **Adding a ReasonCode variant requires (a) classifying it into `src/model.ts` `REASON_PRIORITY` (positive) or `EXEMPT_REASONS` (exemption), and (b) adding the zh+en keys for its families in `src/i18n.ts`** — `scripts/check-reason-parity.mjs` (run in CI, self-tested by `scripts/check-reason-parity.test.mjs`) fails otherwise.

### Kill path (`platform.rs`)

`kill_process(pid, force, start_unix)`: the frontend passes the scan-time `start_unix`; the backend re-reads the process creation time (macOS: `ps -o etime=`; Windows: `GetProcessTimes` on the same handle later used by `TerminateProcess`) and refuses with `KillError::PidReused` if it moved by >5s — killing a recycled PID is a data-loss bug. macOS: SIGTERM/SIGKILL two-button UI. Windows: single "Terminate" button (`TerminateProcess`; there is no reliable graceful kill for detached console processes — deliberate product decision, do not add CTRL_BREAK heuristics).

**Failures cross every IPC boundary as one shape: the engine's `KillError` serde form `{code, message?}`** (`#[serde(tag = "code", rename_all = "snake_case")]`) — the Tauri command returns `Result<(), KillError>`, the CLI writes the same value to stderr as JSON. The four semantic codes (`identity_unknown`/`process_gone`/`pid_reused`/`access_denied`) are localized per frontend; `os` carries verbatim system text and is only ever displayed as-is. Adding a variant obliges **three** places: `platform.rs` `wire_contract_tests`' table, `src/model.ts`'s `KillError` union (a union member with no `switch` arm is a tsc error — that is the point), and `integrations/raycast/src/cli.ts` `killErrorMessage`. The v0.8.1-era `ERR_*:` prefix strings + `includes()` matching were deleted in v0.9.0 (issue #35) — **never reintroduce substring matching on error text**: its failure mode is silent, a missed frontend just dumps raw English at the user. Note `ERR_ACTION_TIMEOUT`/`ERR_SCAN_TIMEOUT` are *not* wire forms — they are frontend-only sentinels minted by `withTimeout` and never cross IPC; `ERR_SCAN_BUSY` is the one remaining backend string, deliberately left alone (scan has a single semantic branch and no second consumer — see issue #35's evaluation).

### Tray / window lifecycle

The window close button is intercepted (`lib.rs` `on_window_event` → hide + `prevent_close()`) — the app lives in the tray; quitting only happens via the tray menu. **macOS runs as an `ActivationPolicy::Accessory` app** (set in `setup`): no Dock icon, no ⌘Tab entry — the menubar-utility identity matches the tray-resident behavior (verified via LaunchServices `type="UIElement"`). **macOS ⌘Q** is handled by replacing the default app menu (`Builder::menu` in `lib.rs`): muda's predefined Quit calls `[NSApp terminate:]`, which tao 0.35 does **not** route through `ExitRequested` (empirically verified — the process just dies; do not "fix" ⌘Q by intercepting `ExitRequested{code: None}`, that event only fires when the last window is *destroyed*). The custom `quit-to-tray` item owns the Cmd+Q accelerator and hides the window instead. Under Accessory the app menu is never *displayed*, but it must still be *built*: AppKit consults the app's mainMenu for key equivalents even when the menu bar isn't shown — webview ⌘C/⌘V/⌘W/⌘Q all route through this invisible menu, so the Edit/Window submenus must stay. Logout / shutdown (AppleEvent quit) still exit for real — deliberate: system-initiated quits must be honored. (Dock-quit no longer exists — there is no Dock icon.) macOS shows counts in the tray *title* (`icon_as_template` gated to macOS); Windows has no tray title — counts go to the *tooltip*. The tray menu (and macOS app menu) also exposes "open data/cache/log/temp folder" items backed by `paths.rs`. Tray menu labels are bilingual: handles are stored in `TrayMenuItems` state (+ `AppMenuItems` for the macOS ⌘Q item) and re-texted by `set_tray_language` (called by the frontend on toggle; initial language from `sys-locale`).

### Logging & per-environment data isolation

`portreaper_core::paths` scopes every persisted directory (config/whitelist, logs, cache, data, app-temp) by build profile: debug builds append a `dev/` subdir, so `pnpm tauri dev` never pollutes the installed app's data (compile-time `cfg(debug_assertions)`, no env vars). The same rule intentionally extends to the CLI: a release CLI shares prod data with the installed GUI, a `cargo run` debug CLI shares `dev/` with `pnpm tauri dev` — don't "fix" that as a coincidence. Identifier/algorithm parity with Tauri's `app_*_dir()` is guarded in **two layers**: `scripts/check-paths-parity.mjs` (static — the `APP_IDENTIFIER` constant vs `tauri.conf.json`, runs in CI + pre-push) and `src-tauri/src/paths.rs assert_matches_tauri` (runtime, at GUI startup — catches algorithm drift, e.g. a tauri upgrade changing its `dirs` major; panics in debug, `log::error!` in release). A one-character split means GUI and CLI/Raycast silently write separate `whitelist.json` files. Logs go through `tauri-plugin-log` to `portreaper-{dev,prod}.log` in the scoped log dir (+ stdout in debug). `src/logger.ts` bridges webview uncaught errors / unhandled rejections into the same file — **its log calls must swallow their own failures** (`.catch(() => {})`): during the startup race the plugin isn't registered yet, a rejecting `error()` call re-enters the `unhandledrejection` listener and self-excites into an infinite loop (real incident: 46 MB of log and a pegged CPU). Never let the logger produce an error it would itself report.

### Windows caveats (no dev machine — CI is the safety net)

`scanner/windows.rs` and the Windows half of `platform.rs` are compile-checked locally via the cross-target command above and compiled+unit-tested in CI, but have **no manual QA**. The Windows release asset is labeled experimental; the acceptance checklist is `docs/TESTING-WINDOWS.md`. When exe paths are unreadable (MSIX/elevated processes), the scanner errs toward *not* flagging (empty exe ⇒ treated as standard install).

## Release / website

Tag push `v*` → `.github/workflows/release.yml`: version-consistency gate → tauri-action matrix (macOS arm64/x64 dmg, Windows NSIS; each leg also builds a `portreaper-cli` binary) → publish job verifies all **6** assets, re-uploads **stable-named** copies (`Portreaper-macos-arm64.dmg`, `Portreaper-macos-x64.dmg`, `Portreaper-windows-x64-setup.exe` + 3 `portreaper-cli-*` binaries), generates `portreaper-cli-SHA256SUMS` (the Raycast extension downloads and verifies against it), and flips the draft to published. The website (`/website`, GitHub Pages via `pages.yml`) hardcodes `releases/latest/download/<stable-name>` URLs, so downloads auto-update on every release with no site changes. Bump versions only via `node scripts/bump-version.mjs X.Y.Z` (syncs package.json, tauri.conf.json, src-tauri/Cargo.toml, crates/portreaper-cli/Cargo.toml, Cargo.lock). Runbook: `docs/RELEASING.md`.
